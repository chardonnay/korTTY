# Release notes

What changed in the current release. The version this guide was built for is shown in the footer.

## v2.18.0

### Terminal

- **Coding agents** — korTTY recognises Claude Code, Codex and Gemini CLI in local shell tabs and classifies each pane as working, blocked on a question, done or idle, and now shows it everywhere: a glyph in the tab title, chips, accent bars, rollups and pane rows in the dashboard (which expands to a waiting agent and offers Send Enter / Esc / Interrupt in the context menu), a dockable **Coding Agents** panel (*View → Coding Agents*, ++ctrl+alt+g++) listing every agent of every window with one-click answers (y, n, Enter, Esc, ↑, ↓, Ctrl+C), Explain, Rename and a prompt box, a status-bar strip, ++ctrl+alt+n++ to jump to the next waiting agent, a badge with the number of waiting agents on the app icon (Dock, Windows taskbar, KDE/Ubuntu launcher; window title elsewhere) and a desktop notification when an agent needs a decision or finishes while you are not looking at its pane. Detection reads the terminal screen locally and can be switched off in *Settings → Terminal → Coding agents*, where the badge and the notifications have their own toggles; the rules are JSON files you can override under `~/.kortty/coding-agents/`. See [Coding agents](../features/coding-agents.md).
- **Control API and `kortty-cli`** — korTTY can now open a local socket so a script or a coding agent on the same computer can list your windows, read any pane, type into it, wait for output, split a local shell, and drive a detected coding agent. It is **off by default** and is switched on under *Settings → Terminal → Control API*, where a status line reports what the listener is actually doing. Nothing is reachable over the network and no other user of the computer can connect: the endpoint lives in an owner-only `~/.kortty/control/` directory and needs a token that is regenerated on every start. Every action is logged with byte counts only, never terminal text, and the first time a program types into a pane you get one desktop notification, so a takeover is never silent. An administrator can deny the feature outright with the `control-api` policy key. The `kortty-cli` client ships beside the application in every native package and handles discovery, authentication and exit codes for you. See [Control API](../reference/control-api.md) and [Control CLI](../reference/cli.md).
- **Prompts and Control API pastes can no longer end their bracketed paste early** — a bracketed-paste end marker (`ESC[201~`, or its 8-bit form in a single-byte encoding) inside the text of a coding-agent prompt or a bracketed `pane.send_text` closed the paste korTTY had wrapped around it, so every following line reached the program as typed input and was submitted on its own. korTTY now removes the start and end markers from every prompt and from the text of a bracketed `pane.send_text`, including markers that only form once an inner one is removed and, in a Windows-1252 pane, the `›` that this encoding sends as the 8-bit introducer; an unbracketed `pane.send_text` or `pane.run` still keeps them. See [Typing into a pane](../reference/control-api.md#typing-into-a-pane).
- **Terminal pastes can no longer end their bracketed paste early** — korTTY passed pasted text to the terminal unchanged, so a bracketed-paste end marker (`ESC[201~`) inside it closed the paste the terminal wrapped around it, and every following line reached the shell as typed input and ran on its own. Every terminal paste (the paste shortcut, *Edit → Paste*, **Paste** in the right-click menu and a middle-click) now goes through korTTY, which removes the start and end markers from the text, including their 8-bit form in a single-byte character encoding, before it wraps the paste itself. A pane also no longer keeps bracketed paste switched on after a reconnect or a terminal reset (`reset`), which wrapped pastes in markers that the next program might not understand. See [Pasting text](../features/terminal.md#pasting-text).
- **Paste protection** — a terminal paste that could run commands or hide something now asks first. A paste with line breaks asks unless the program in the pane uses bracketed paste, a paste with control characters (such as Escape or Ctrl+C) or invisible direction-changing characters asks even then, and a paste larger than 5 KiB always asks. The dialog shows the pane, the number of lines, the size, the reasons and a preview in which hidden characters are visible; **Cancel** is the default button, so pressing ++enter++ by habit never pastes. Choose when it asks under *Settings → Terminal → Paste protection*: **Always** asks for every paste with a line break, **Off** only keeps the size check, and a size of 0 turns that off. See [Paste protection](../features/terminal.md#paste-protection).
- **Paste line by line into slow devices** — switches, routers and console servers behind SSH can lose input that arrives too fast, so a pasted configuration arrived with characters or lines missing. *Settings → Terminal → Paste protection → Pause after each pasted line* (0 to 1,000 ms, off by default) now sends a paste with several lines one line at a time with that pause. The pane shows how far the paste is, takes no keys meanwhile so nothing you type lands between two lines, and ++esc++ stops the rest; broadcast mode leaves the pane out until it is done. See [Pasting into slow devices](../features/terminal.md#pasting-into-slow-devices).
- **Drop text onto a terminal** — text dragged from a browser, an editor or another korTTY window and dropped onto a terminal was ignored; only files were taken, to be copied to the server. Dropped text is now pasted into the pane under the pointer, which becomes the focused pane, through paste protection like any other paste, and it is always copied, so the application you drag from keeps it. The setting is now called *Settings → Terminal → Allow drag and drop into the terminal* and covers files and text; with the enterprise policy's internal clipboard mode, text from other applications is refused. See [Dropping text](../features/terminal.md#dropping-text).
- **Files dropped onto a terminal land where you dropped them, and only there** — a file drop always went to the pane you had last clicked, even when you dropped it onto another pane of a split tab; it now goes to the pane under the pointer, which becomes the focused pane. After `su`, `sudo -i` or a nested `ssh` the files were still uploaded with the tab's own login into the directory the inner shell reported, which may belong to another user or host; korTTY now refuses such a drop with a message, and **Copy as file(s) to terminal directory** and **Copy folder to terminal directory** in the Snippet Manager do the same. A dropped folder containing a link to one of its parent folders no longer makes the copy run until it fails: links to folders are skipped and counted in the progress window, while links to files are still copied with their content. Each drop also kept one SFTP channel of the terminal's SSH session open until the tab closed, so after many drops the server could refuse new channels; the channel is now closed when the copy ends, and a drop onto a session that has just closed says so instead of failing with an internal error. See [Dropping text](../features/terminal.md#dropping-text).
- **A shell on another host is recognised from its directory reports** — shells that report their directory with OSC 7 also name their host. korTTY now remembers the host of the first report of your own session and, when a later report names another host, no longer moves the tracked terminal directory there and treats the pane as running elsewhere: file drops and snippet copies are refused as after `su` or a nested `ssh`, until the original host reports again or the tab reconnects. The full name of the host, `localhost` and reports without a host count as the same host. See [Dropping text](../features/terminal.md#dropping-text).
- **Busy sessions on slow links are no longer cut off as lost** — korTTY declared an SSH connection lost when two liveness probes in a row went unanswered, even when the server was still sending data and the reply was only queued behind it, for example a large output or a file transfer over a slow link. An unanswered probe now only counts while nothing arrives from the server at all, so such a session stays open, and a dead network is still noticed within about ten seconds. See [Connection loss and automatic reconnect](../features/terminal.md#connection-loss-and-automatic-reconnect).
- **Command timestamps stay on their command lines** — once the scrollback had reached its limit, the marks in the command timestamp sidebar drifted one row further from their command with every new line of output, and a new prompt on the bottom row got no mark of its own. Marks now move with their lines, disappear when their line leaves the scrollback, and are removed by **Clear Buffer**. The dates in the sidebar and its hover popup follow the UI language instead of a fixed German order, and **Duplicate** and **No Group** in the tab context menu are translated instead of always German. See [Terminal settings](../reference/settings/terminal.md#notes).
- **Anonymous usage statistics now cover coding agents and the Control API** — if you allowed anonymous statistics, korTTY also reports which agent kinds are detected, how often agent notifications fire, which Control API methods are used and whether the coding-agent and Control API settings are on. Only kinds, states, method names and counts are sent — never terminal text, prompts or pane names. See [Anonymous data](anonymous-data.md).
- **Anonymous usage statistics now cover the command palette, multi-exec and session restore** — if you allowed anonymous statistics, korTTY also reports which kind of command palette row you run, when you turn multi-exec on or off and how far it reaches, when the previous session is restored and how, and whether you changed the quick-select letters or patterns, the tab-title and tab-order switches or any shortcut. Only kinds, flags and rounded counts are sent — never search text, names, hosts, patterns or what you type. See [Anonymous data](anonymous-data.md).
- **Cmd/Ctrl+W and the Dashboard's Close ask before closing a busy terminal** — the tab's close button asks before it closes a tab with split panes or a command that is still running, but **Close Tab** (++cmd+w++ on macOS, *File → Close Tab*) and **Close** in the Dashboard closed such a tab straight away and ended the running command. All three now ask the same question; an idle terminal at its prompt still closes immediately, and a connection set to *Close tab without confirmation* never asks. A terminal closed with **Close Tab**, the Dashboard's **Close** or **Close All Tabs** is now also released like one closed with its close button, instead of staying in memory with its status-bar timer still running. See [Working with tabs](../features/terminal.md#working-with-tabs).
- **Tabs that close on their own are fully released** — when a split pane was left as the last pane and its shell exited, or ++ctrl+d++ closed a local cmd or PowerShell tab, the tab closed without the cleanup its close button runs: korTTY still counted that pane as connected, so with **Configuration > Prevent System Sleep** checked the computer was kept awake, and a shell closed with ++ctrl+d++ kept running in the background. Such tabs now close exactly like a tab closed with its close button.
- **Navigation keys reach programs the way they expect them** — korTTY used to send the arrow keys, Tab, Home/End, Page Up/Down, Insert/Delete and the F-keys as fixed sequences without their modifiers, so ++ctrl+left++ and ++shift+tab++ arrived as plain Left and Tab and ++shift+f1++ as F1. They are now encoded the xterm way and follow the program's cursor-key mode, so word movement (++ctrl+left++ / ++ctrl+right++, ++option+left++ / ++option+right++ on macOS) and back-tab work in the shell, `mc` and `vim`. ++shift+page-up++ / ++shift+page-down++ now scroll korTTY's scrollback, ++ctrl+tab++ switches tabs while the terminal has the focus, editing the find bar's search text no longer types into the shell, and broadcast mode mirrors these keys to every pane, encoded for each. See [Keyboard shortcuts](../reference/keyboard-shortcuts.md#terminal).
- **Broadcast mode no longer freezes the window when one server stalls** — the keys mirrored into the other panes were sent on the thread that draws the window, so a pane whose SSH connection had stopped responding froze korTTY on every keystroke. They are now sent in the background, still in the order you typed them for each pane, so only the stalled pane waits while the window and the other panes keep reacting. See [Broadcast mode](../features/terminal.md#broadcast-mode).
- **Broadcast mode keeps AI agents and passwords where they belong** — the keys typed in broadcast mode reached every pane of the tab, so `agent …` and ++enter++ started an AI agent run in each pane, a mirrored ++y++ could approve what a coding agent waiting for a decision asked in another pane, and a sudo password typed in one pane ran as a command in the panes at an ordinary prompt, where it stayed in their shell history and session journal. Now the agent shortcut starts a run only in the pane you type in, panes where an AI agent runs or a coding agent waits for your decision get no mirrored keys (the **Extras** submenu of a pane's right-click menu says how many are left out), and while you type at a password prompt your keys go only to the panes at a password prompt too. See [Broadcast mode](../features/terminal.md#broadcast-mode).
- **Copying and pasting in broadcast mode no longer reaches the other panes** — on Windows and Linux, ++ctrl+shift+c++ and ++ctrl+shift+v++ still produce the control character of ++ctrl+c++ or ++ctrl+v++, and broadcast mode sent it to the other panes of the tab: copying a selection interrupted the program running in each of them, and pasting made their shells insert the next key literally. A key now goes to the other panes only when the pane you type in sends it to its own program as well, which also keeps the keys of menu commands out of them. See [Broadcast mode](../features/terminal.md#broadcast-mode).
- **Ctrl+L and Ctrl+F reach the shell on Windows and Linux** — the terminal's own Clear Buffer and Find took these keys, so ++ctrl+l++ wiped the scrollback instead of redrawing the screen in bash, psql or a REPL, and ++ctrl+f++ never moved the cursor forward or paged forward in `less`. Both keys now go to the shell; Clear Buffer and Find stay in the terminal's right-click menu and Find in *Edit → Find…*, while ++cmd+k++ and ++cmd+f++ on macOS are unchanged. On Linux a selection copied automatically also becomes the X11 primary selection, so a middle-click pastes it in other applications. See [Keyboard shortcuts](../reference/keyboard-shortcuts.md#terminal).
- **The ANSI colors and the selection color on the Colors tab now take effect** — the 16 color pickers in *Settings → Colors* were never saved, and the terminal ignored the **Selection** color too. Both now apply to every open terminal as soon as you save, and terminal recordings use the same colors as the screen. Settings you never changed keep the built-in palette and inverse-video selection, so nothing looks different until you customize a color. **Bold as bright color** still affects recordings only. See [Colors](../reference/settings/colors.md).
- **Menu commands follow the pane you type in** — in a split tab, *Edit → Copy*, *Edit → Paste*, *Edit → Find...*, the AI actions and a recording of the active split used the pane you had last clicked. When the keyboard focus reached another pane some other way, for example with a middle-click, or stayed in the original pane after a split that showed a connection dialog, they acted on a different pane than the one receiving your typing, and closing one pane moved them to the first pane even when you were typing in another. They now use the pane that has the keyboard focus. See [Split operations](../features/terminal.md#split-operations).
- **No pane close button on a tab with a single terminal** — the × in a pane's top-right corner, meant for closing one pane of a split tab, also showed when the tab had only one pane, and clicking it there ended that terminal's session at once, without the question the tab's own close button asks before it closes a busy terminal. The × now shows only while the tab has more than one pane. See [Split operations](../features/terminal.md#split-operations).
- **Same-server splits open on the pane's own server** — **Split Right (same server)** and **Split Down (same server)** always opened a session to the tab's server, so splitting a pane you had opened with **Split Right (new connection)** or **Split Down (new connection)** to another server put the new pane on the wrong host. They now open on the server of the pane you split, with the sign-in that pane used, and so do the panes split from it; the server access policy is checked for that server. See [Split operations](../features/terminal.md#split-operations).
- **Move between split panes from the keyboard, and see which one has the focus** — nothing showed which pane of a split tab the keyboard was in, and reaching another pane needed the mouse. A blue ring now marks the focused pane while the tab has two or more panes, and a dimmer ring stays on the pane the menu commands act on while you work in another window or panel; it never changes the size of the terminal. ++cmd+option++ (macOS) or ++ctrl+alt++ (Windows, Linux) with an arrow key moves the focus to the pane on that side, and the new *View → Panes* menu has the same commands, **Next Pane**, **Previous Pane** and the tab's broadcast mode. With a single pane the keys still reach the program in the terminal. Screen readers name each pane *Pane 2 of 3*. See [Split operations](../features/terminal.md#split-operations).
- **Split and close panes from the keyboard and the menu bar** — a pane could only be split or closed with the mouse, from its right-click menu or its ×. ++cmd+shift+o++ (macOS) or ++ctrl+shift+o++ (Windows, Linux) now splits the pane the keyboard is in, on that pane's own server like **Split Right (same server)**: the new pane goes to the right of a wide pane and below a tall one, so repeated splits keep the panes roughly square, and the keyboard moves into it. *View → Panes* has **Split Pane**, **Split Right**, **Split Down** and **Close Pane**, which closes the pane the keyboard is in and is disabled in a tab's last pane. On Windows and Linux ++ctrl+shift+o++ no longer reaches the shell; ++ctrl+o++ still does. See [Split operations](../features/terminal.md#split-operations).
- **Zoom a split pane** — ++cmd+shift+enter++ (macOS) or ++ctrl+shift+enter++ (Windows, Linux), or *View → Panes → Zoom Pane*, lets the pane the keyboard is in fill the whole tab, and pressing it again shows all panes with every divider where it was. A badge on the zoomed pane says how many panes are hidden; they keep running at their size, so their programs see no resize. In broadcast mode the badge also says how many hidden panes still receive what you type, and turns amber. Splitting, closing or moving a pane and moving the focus to another pane show all panes again. With a single pane the key still reaches the program as ++enter++. See [Split operations](../features/terminal.md#split-operations).
- **Multi-exec: type into chosen panes of several tabs and windows at once** — broadcast mode only reached the panes of one tab. Now you choose panes in any tab of any window, with *Extras → Multi-exec: Include This Pane* in a pane's right-click menu, the tab's right-click menu, *View → Multi-exec* or a Dashboard row, and what you type in one of them goes to all the others, each key encoded for the program in each pane. Paste, snippets and input-method text stay in their pane, and the safety rules of broadcast mode apply: panes where an AI agent runs or a coding agent waits for your decision get nothing, an agent run starts only where you type, and a password typed at a prompt goes only to panes at a password prompt. There is no confirmation, but the chosen panes show an amber outline and a *Multi-exec* badge, their tabs and Dashboard rows an amber icon, and every window's status bar a chip with the number of panes, tabs and windows and a **Stop** link. In broadcast mode the panes and the tab now show the same markers. See [Multi-exec](../features/terminal.md#multi-exec).
- **Window shortcuts leave no character behind in the terminal** — on Windows and Linux a key combination can still produce a typed character after korTTY has acted on it. For ++ctrl+shift+l++ (Show / Hide Menu Bar) and ++ctrl+shift+f++ (Terminal-only Fullscreen) korTTY now discards that character, as it already did for the zoom keys, so it can neither reach the shell nor be mirrored to the other panes in broadcast mode. See [Keyboard shortcuts](../reference/keyboard-shortcuts.md#general).
- **Keyword highlighting in terminal output** — korTTY can now color errors and warnings, IP and MAC addresses, and the interface names and link states of switches and routers as output arrives, with three built-in rule sets (**Errors and warnings**, **Network addresses**, **Network devices**). It is off until you switch it on: ++ctrl+shift+h++ (++cmd+shift+h++ on macOS) toggles it for the focused pane, and *View → Highlighting* or **Highlighting** in the terminal context menu picks the set. The choice applies to that pane for the running session; a new split inherits it. Highlighting only changes how text looks — copying, logs and the AI features see the original output — it skips full-screen programs such as `vim` and `less`, runs on a background thread so a fast `cat` keeps its speed, and gives each rule a time limit so a slow pattern cannot stall the terminal. See [Keyword highlighting](../features/highlighting.md).
- **A default highlighting rule set for every terminal** — *Settings → Terminal → Keyword highlighting* can now pick a rule set that every pane shows without a choice of its own, so highlighting is on in every new and open terminal without pressing the shortcut in each one. A set chosen for a pane in a menu or with the shortcut, including **None**, still wins for that pane. The same section has a master switch that turns highlighting off everywhere and greys out the menus, and an option to highlight inside full-screen programs such as `vim`, `less` and `htop`, which stays off by default because they redraw constantly. The default rule set is **None**, so nothing changes until you choose one, and every change applies to open terminals as soon as you save. See [Default rule set and settings](../features/highlighting.md#default-rule-set-and-settings).
- **Your own highlighting rule sets** — the new rule-set editor (*View → Highlighting → Manage Rule Sets…*, the **Highlighting** submenu of the terminal context menu, or **Edit Rules…** in *Settings → Terminal*) creates and changes rule sets of your own: words or regular expressions, whole word and ignore case, the matched text or the whole line, a theme or custom text and background color, and bold, italic or underline, in a priority order you set. The built-in sets stay read-only, and **Duplicate** turns one into an editable copy. A live preview shows a test text the way a terminal pane would, with the hits of each rule and a warning for a rule that is slow or runs out of its time limit, and **OK** stays disabled while a rule cannot work. Your sets appear in the highlighting menus and as the default rule set as soon as you confirm the editor. See [Your own rule sets](../features/highlighting.md#your-own-rule-sets).
- **A highlighting rule set per connection** — the connection editor's *Terminal Settings* tab has a new **Terminal behavior** section where **Keyword highlighting** picks the rule set that connection's terminals show, for example **Network devices** for your switches: **Use the default** follows *Settings → Terminal*, **None** keeps the connection plain even when a default is set, or pick a built-in set or one of your own. A pane shows the set chosen for it in a menu or with the shortcut first, then its connection's set, then the default. Saving in the Connection Manager applies the change to open terminals in every window, a split to another server follows that server's connection, and the choice is stored in `connections.xml` and survives duplicating, exporting and importing; a set that does not exist on this computer, for example from a shared teamwork file, is skipped. See [Rule set per connection](../features/highlighting.md#rule-set-per-connection).
- **Rename terminal tabs** — right-click a tab and choose **Rename Tab…**, or use *File → Rename Tab…*, to give a terminal tab a name of its own in place of the connection's name; the coding-agent glyph, the tab group and the `(DISCONNECT)` marker stay. An empty name shows the connection's name again. Projects save the name and restore it, and the Coding Agents panel and the Control API's `tab.list` show it. See [Working with tabs](../features/terminal.md#working-with-tabs).
- **Close other tabs or the tabs to the right** — right-click a terminal tab and choose **Close Other Tabs** or **Close Tabs to the Right**, or use the *File* menu entries of the same name for the active tab. The tab you chose stays open and becomes the active tab. Rather than one question per tab you are asked at most once, and only when some of the closing terminals have split panes or a command that is still running; an editor with unsaved changes still asks on its own, and a Cancel keeps every tab open. See [Working with tabs](../features/terminal.md#working-with-tabs).
- **Jump to a tab with Cmd/Ctrl+1 to 9** — ++cmd+1++ to ++cmd+8++ on macOS and ++ctrl+1++ to ++ctrl+8++ on Windows and Linux select the first to eighth tab of the window, and ++cmd+9++ / ++ctrl+9++ the last one, with the top-row or the numpad digits and also while a terminal has the focus. No digit is left behind in the terminal or mirrored to the other panes in broadcast mode. On Windows and Linux only ++ctrl++ with a digit jumps, so ++alt-graph++ characters and ++ctrl+shift+6++ still reach the terminal, while ++ctrl+1++ to ++ctrl+9++ themselves no longer do (the terminal never sent them as keys of their own). See [Keyboard shortcuts](../reference/keyboard-shortcuts.md#general).
- **Reopen closed tabs** — ++cmd+option+shift+t++ on macOS and ++ctrl+alt+shift+t++ on Windows and Linux, *File → Reopen Closed Tab* or **Reopen Closed Tab** in a terminal tab's right-click menu bring back the terminal tab you closed last, with a new session to the same connection and with its tab group, its name and its terminal effect; its output and split panes are not restored. *File → Recently Closed* lists the last 25 closes, newest first: a single tab, the tabs one **Close Other Tabs**, **Close Tabs to the Right** or **Close All Tabs** closed, which reopen together, or the tabs of a window you closed while korTTY kept running. Tabs whose session ended on their own and everything that closes when you quit are not listed. A reopened tab signs in like **Connect** in the Connection Manager, with the saved connection as it is now and the server access policy checked first; the list never keeps a temporary SSH key, so a session that used one asks for a new key. The *Close all tabs?* question no longer says this cannot be undone. See [Working with tabs](../features/terminal.md#working-with-tabs).
- **Open recent connections and projects** — *File → Open Recent* lists the saved connections you used last and the projects you opened or saved last, so you get back to them without the Connection Manager or the file dialog. Under **Connections** are up to 10 connections, newest first, as at the top of Quick Connect; choosing one opens a tab that signs in like **Connect** in the Connection Manager, with the server access policy checked first. Under **Projects** are up to 10 project files, followed by the other projects in `~/.kortty/projects`; choosing one opens it like *File → Open Project…*, and a file that was moved or deleted is left out. **Clear List** empties the menu without deleting a connection or a project file. The paths of the recent projects are kept in `global-settings.xml`, so they are part of configuration backups. See [Open Recent](../features/projects.md#open-recent).
- **Split panes come back with a project, on their own servers** — opening a project rebuilt a tab's split panes only after a fixed one-second wait during which the window froze, then showed a *Connecting* dialog for every pane, put every pane on the tab's server even when it had been opened on another one, and could put the panes of a nested layout in the wrong places with the dividers in the middle. The panes now open once the tab is connected, one after the other in the background, each in its saved place with the saved divider positions. A pane opened on another server comes back on that server, signing in with what is stored, and every pane passes the server access policy. A pane that would need a password, a new temporary key, a locked vault or a blocked server stays closed with the panes split from it, and the status bar says how many panes were not reopened and why. korTTY drops a pane's working directory and scrollback reference from every project file it opens or saves, so a shared project cannot choose the folder a local shell starts in. See [Split panes](../features/projects.md#split-panes).
- **Projects keep every window and its active tab** — *File → Save Project* saved only the window you chose it in, and *File → Open Project* put the tabs of every saved window into one window, ignored which tab had been active and set the saved bounds without checking that the screen was still there. A project now keeps every open window with its position, size and maximized state, its tabs and the tab that was active. Opening it gives the first window to the window you open it from and opens each further window in a new window, while the windows already open keep their tabs; a project file holding several windows therefore no longer lands in one window. A window whose screen is no longer attached opens centred on the main screen, the tabs come back in their saved order and tab groups, and each window selects its active tab, also when that is a remote file that is still downloading. See [Windows](../features/projects.md#windows).
- **Projects reopen local shells and list the tabs that need you in one bar** — opening a project skipped every local shell tab, because its authentication field says "password" by default, and silently skipped every tab whose password was not saved or sat in the locked vault; an expired temporary SSH key was renewed without asking. Opening a project now asks nothing while it opens the tabs: local shells, SSH key logins, saved passwords and valid temporary keys open right away, and every other tab is listed in a bar above the status line of its window, for example *Tabs not reopened: sign-in needed (2) · vault locked (1)*, which never blocks the window. **Connect…** asks for each missing password or new temporary key once per connection and opens the tabs with their saved screen, group, name and split panes, **Unlock Vault…** opens the tabs whose password is in the vault (in every window, also when you unlock the vault from the menu), **Details** names every tab and why it did not open, and **Dismiss** forgets them. Servers the server access policy blocks, deleted connections and missing local files are listed there instead of being skipped or shown one dialog at a time. A temporary SSH key that korTTY could not decrypt because the vault was locked at startup now counts as one that needs renewing, here and wherever you connect, instead of starting an SSH key login without a key. See [Tabs that wait for you](../features/projects.md#tabs-that-wait-for-you).
- **Restore the previous session** — korTTY now saves your open windows and tabs while it runs, a couple of seconds after each change and once more when you quit, and *File → Restore Previous Session* opens what was open before this start, after a restart or a crash: every window with its position, size, tabs, split panes and active tab. The tabs open like those of a project with Auto-Reconnect and ask nothing; a tab that needs a password, a new temporary SSH key or the locked vault waits in the restore bar. No screen text, scrollback, password or temporary SSH key is saved, the files in `~/.kortty/session/` are readable only by you and are not part of backups, and a session without tabs never replaces the previous one. The Recently Closed list now survives a restart as well, kept as the ids of saved connections only. See [Previous session](../features/projects.md#previous-session).
- **The previous session is offered at startup** — when korTTY starts, a bar above the status line now offers the windows and tabs that were open before, for example *Restore the windows and tabs from before this start? ### SSH and security

- **SSH tunnels now really open** — tunnels configured on a connection were saved, imported and shared, but never opened. korTTY now opens the enabled ones once per terminal tab after login, closes them before a reconnect and opens them again afterwards, moves them to another pane of the same server when you close the pane they run on, and shows `Tunnels: 2/3 active` with the first error in the tab's status bar (hover for every tunnel). Because tunnels that never did anything would otherwise start listening silently after the update, korTTY asks once per connection before it opens them, and again when the tunnels or the server change. A remote tunnel listens on the SSH server's loopback address unless you name another one, shared (Teamwork) connections never open remote tunnels and may only listen on `localhost`, and administrators can forbid tunnels with the new `allow-port-forwarding` policy key. Remote tunnels that earlier versions imported from PuTTY Connection Manager carry the bind address `0.0.0.0`; the confirmation, the tunnel list and the status bar mark them as reachable from other computers, so set their **Remote bind address** to `localhost` if the forwarded port should stay private to the server. See [SSH Tunnels](../features/tunnels.md).
- **The tunnel editor says what listens where, and Enable SSH tunnels works** — the tunnel dialog now labels its fields after their role for each type (**Local bind address**, **Remote bind address**, **Local host** as a remote tunnel's target), lists the listener first and warns when other computers can reach it; the tunnel list shows remote tunnels listener first instead of reversed and no longer shows German text for SOCKS proxies. **Enable SSH tunnels**, which nothing ever read, now switches every tunnel of the connection on or off, and saving the connection applies tunnel changes to open tabs right away, so switching tunnels off closes them. **Cancel** now discards tunnels added, edited or removed in the connection editor, which were kept before. PuTTY Connection Manager imports bind remote tunnels to `localhost`. See [SSH Tunnels](../features/tunnels.md#the-tunnel-list).
- **The terminal encoding now takes effect** — *Settings → Terminal → Encoding* was never read, so every SSH session was decoded as UTF-8 and servers that write ISO-8859-1, ISO-8859-15 or Windows-1252 showed broken umlauts. The setting now applies to SSH connections, and each connection can choose its own **Character encoding** on the *Connection* tab of the connection editor. Local shells stay UTF-8 unless their connection sets an encoding, and Mosh is always UTF-8. A value you picked in an earlier version, when it had no effect, is not applied on its own: SSH sessions stay UTF-8 until you save the settings after opening the Terminal page, where a note points this out. Text that the [Control API](../reference/control-api.md#typing-into-a-pane) types into a pane follows the pane's encoding as well. See [Character encoding](../features/connections.md#character-encoding).
- **Temporary SSH keys are no longer left in the temp folder** — every connect, split and SFTP session with a temporary SSH key wrote the private key to a file in the system temp folder that was never deleted, so the key stayed on disk long after it had expired, and the debug log recorded the beginning and end of the key text. Temporary keys are now read in memory only and never logged, and key files that earlier versions left behind are deleted at the next start when they belong to you. See [Security](../reference/settings/security.md).
- **Scheduled jobs keep temporary keys off the disk too** — a JobScheduler job with a temporary SSH key now authenticates in memory like a terminal tab. Only an Rsync job still needs the key as a file for its external `ssh`; that file is created owner-only from the start and deleted when the job ends or its connection fails, instead of staying in the temp folder.
- **JMX monitoring shows the connections that are really open** — the `de.kortty:type=SSHClient` MBean always reported 0 active connections and no names, because it read a session list that nothing ever filled. `ActiveConnectionCount`, `ActiveConnectionNames` and `ConnectionStatistics` now list every live SSH and Mosh terminal connection (each split pane counts, local shells do not), and `BufferedTextSize`, which was never measured, stays at 0 for existing JMX clients. See [Logging and diagnostics](../reference/architecture.md#logging-and-diagnostics).

### Security

- **Enterprise policy for the new terminal features** — administrators can now manage paste protection, OSC 52, multi-exec and session restore from `kortty-policy.toml`. `paste-warning` in `[rule.terminal]` sets the least a paste warning asks, on top of *Settings → Terminal*, a connection's own warning and teamwork connections; `allow-osc52-clipboard-write = false` in `[rule.security]` keeps programs from putting text on the clipboard; `multi-exec = "deny"` in `[rule.features]` locks every way into multi-exec and broadcast mode while **Stop Multi-exec** keeps working; `session-restore` in `[rule.terminal]` sets and locks what korTTY does at startup with the previous session; and `session-restore-output` in `[rule.terminal]` sets and locks whether the output of each terminal pane is restored with it. Managed settings carry the "Managed by your organization" hint (the paste warning still offers stricter choices), and the fail-safe lockdown of a broken policy file now asks before every multi-line paste, forbids OSC 52 and multi-exec, reopens nothing at startup and saves no terminal output for it. See [Policy configuration](../reference/enterprise-policy.md).
- **Links in terminal output can no longer start local programs** — a program or server could print an OSC 8 link (the kind `ls --hyperlink` prints) with a `file:` target, and a single click opened that file with its associated application, which runs scripts and programs, on Windows even from a network share. korTTY now opens only `http`, `https`, `ftp`, `ftps` and `mailto` links, in your browser or mail program. `file:`, `news:` and every other link stays plain text, and so does a link with control characters, invisible bidi characters or more than 8 KB. A mail link may only fill in recipients, subject, body and in-reply-to, because some mail programs attach the local file an `attach` field names. See [Links in terminal output](../features/terminal.md#links-in-terminal-output).
- **Server output can no longer start an AI agent run** — korTTY reacted to an escape sequence (`ESC ] 777 ; korTTY-agent`) anywhere in the output of an SSH session, such as a file shown with `cat`, a login banner or anything a compromised server sends. It opened the AI agent run dialog filled in with a prompt and inline options such as `root=true` chosen by the server, or started the run right away when the per-run setup dialog was turned off, and the same sequence moved the working directory korTTY tracks for the session. korTTY now ignores these sequences, so an agent command in the terminal starts a run only when you type or paste it. Prompt detection through OSC 133 markers and directory tracking through the shell's OSC 7 reports are unchanged. See [Terminal agent shortcut commands](../features/ai-assistant.md#terminal-agent-shortcut-commands).
- **An overlong escape sequence in terminal output can no longer close the tab** — an escape sequence padded with more than about a thousand characters that the terminal cannot place in it, or with one such character and hundreds of parameters, crashed the terminal emulator, which ended the session and closed its pane or tab. A malicious server, a file shown with `cat` or a line in a log was enough. korTTY now drops what does not fit, as xterm does with too many parameters, and goes on showing the output that follows; escape sequences of normal length are read exactly as before.
- **Unlock the vault after startup** — with *Require master password on startup* turned off, korTTY started with the vault locked and offered no way to enter the master password later. *Configuration → Security → Unlock Vault…* now opens the vault mid-session, and the "vault locked" messages for saving keys and passwords, AI Swarm, guide questions and workflow scripts have an **Unlock Vault…** button that continues the action once the vault is open. Temporary SSH keys that a locked start could not decrypt are restored on unlock instead of being lost on the next save. See [Unlocking the vault later](../features/security.md#unlocking-the-vault-later).
- **Renamed and deleted folders no longer leave host-key verification switched off** — turning off host-key verification for a folder in the Connection Manager stored the folder's name, and renaming or deleting the folder left that entry behind, so a new folder that later reused the name, or a folder renamed to it, silently connected without verifying host keys. Renaming a folder now moves the setting, and that of its subfolders, to the new name, deleting a folder removes it, and when a rename merges two folders verification stays off only if it was off in both. See [Relaxing host-key verification](../features/security.md#relaxing-host-key-verification).

### Connections

- **Password targets behind a password jump server now connect** — the terminal handed the master password only to targets that log in with an SSH key, and the SFTP tab not even to a temporary key, so a password or keyboard-interactive target failed on the jump server's stored password with "vault is locked" although the vault was open — and korTTY kept repeating that failed attempt through the whole retry count. The jump password now works whatever the target's authentication. Failures that another attempt cannot fix — a jump password that is missing, locked in the vault or cannot be decrypted, an incomplete jump setup, a rejected jump-server host key, an SSH key file that is missing or cannot be read — are reported once and no longer retried or reconnected automatically, and with a locked vault korTTY no longer contacts the jump server at all. See [When the jump server cannot be used](../features/jump-server.md#when-the-jump-server-cannot-be-used).
- **Saved local shells keep their shell in Quick Connect and through export and import** — picking a saved Local Shell connection in Quick Connect left its shell, custom command and start directory out of the form and started the platform's default shell instead, for example zsh instead of the saved fish, and importing a korTTY export turned Local Shell and Mosh connections into SSH connections and dropped the shell. Quick Connect now shows the saved shell and start directory and starts that shell, including a command the shell list cannot show, such as `wsl.exe -d Ubuntu`, unless you pick another one; an import keeps the protocol, the shell command and the start directory. See [Local Shell](../features/connections.md#local-shell).

### SFTP file manager

- **Edit server files in your own editor** — **Edit in External Editor** in the SFTP Manager downloads a server file into a private temporary folder, opens it in your text editor (set one under *Settings → SFTP Manager → External editor*, such as `code --wait {file}`, or use the system's text editor) and uploads every save automatically, keeping the file's permissions and owner. A **Remote edits** list shows each file with its last upload, **Upload now** and **Stop**; when the file was changed on the server meanwhile, korTTY asks before overwriting it. The editor is never started through a shell, file names are cleaned up, and the local copy is deleted when you stop, close the tab or quit. See [Editing in your own editor](../features/sftp.md#editing-in-your-own-editor).
- **Edit server files as root** — **Open With → Edit as Root (sudo)...** in the SFTP Manager opens a root-only file such as one under `/etc` in your own editor and writes every save back through sudo. Saves go to a staging folder owned by root, are checked by size and SHA-256 and only then written into the file in place, so it keeps its owner, permissions and labels and is never left half written. korTTY tries sudo without a password first, then asks in a masked dialog (or uses the JobScheduler's saved sudo password once you allow that for the server); the password is wiped when you stop and never reaches a command line or a log. Symbolic links are shown and confirmed first, the row in **Remote edits** carries a **sudo** badge, and the new policy key `sftp-sudo-edit` can switch it off. See [Editing as root](../features/sftp.md#editing-as-root).
- **The SFTP Manager follows the snippet editor policy** — the enterprise policy's `load-into-snippet-editor` key restricted only files opened from the terminal; the SFTP Manager's **Edit in Snippet Editor** ignored it and could write back to the server. Now `read-only` opens server files without **Overwrite file** and **Save as...**, and `deny` disables **Edit in Snippet Editor** and **Open image** for server files; local files are not affected. See [Editing files with Snippet Editor](../features/sftp.md#editing-files-with-snippet-editor).
- **Extract archives on the server** — **Extract Here...** in the SFTP Manager's remote context menu unpacks a ZIP, tar (also `.tar.gz`, `.tar.bz2`, `.tar.xz`) or 7z archive on the server into a new folder next to it, without downloading it; a taken folder name gets ` (1)`, ` (2)` and so on, so nothing is ever overwritten. The archive is checked before anything is written and refused when an entry would land outside the new folder; it is unpacked into a private staging folder, every symbolic link is checked again, and a failure or **Cancel** removes the partial result. Password-protected archives are refused, and a missing `unzip`, `tar` or `7z` is named in the error. See [Extracting archives on the server](../features/sftp.md#extracting-archives-on-the-server).
- **Search subfolders on the server** — the SFTP Manager's search only filtered the folder shown. With **Include subfolders** checked, ++enter++ in the remote search field now searches that folder and everything below it on the server, with the same wildcards, up to 10 levels, 5000 results and 60 seconds. The results list each hit with its path below the folder and say when a limit stopped the search; double-clicking a hit opens its folder with the hit selected, **Back to folder** returns, and ++esc++ stops the search. korTTY uses `find` on the server when it can, with symbolic links never followed and, by default, without crossing into other mounted file systems, and otherwise walks the folders over SFTP. See [Searching subfolders on the server](../features/sftp.md#searching-subfolders-on-the-server).
- **Server archives no longer expose their password** — a password for a ZIP or 7z archive created on the server was passed to `zip` or `7z` on the command line, where every other user of that server could read it in the process list. These tools only take a password that way or from a terminal, so the archive dialog for server files no longer offers a password and explains why; archives created on your computer can still have one, and server archive commands now quote every path and treat a path starting with `-` as a file, never as an option.
- **Open SFTP Here on the terminal's own session** — the SFTP Manager always logged in again, with a second password or MFA prompt, a second jump-server hop and the CyberArk access reason asked again, and it started in the login folder for the tab's connection even when a split pane ran another one. *Connections → Open SFTP Here*, **Open SFTP here** in a terminal tab's and a pane's right-click menu, the command palette and *Connections → SFTP-Client...* with a terminal in front now open SFTP on the focused pane's own SSH session, as that pane's user, in the folder its shell is in. After `su` or a nested `ssh`, or with a shell startup command, it starts in the login folder and says why. Each pane gets its own tab, closing it never closes the terminal, Reconnect uses the pane's session again or offers a separate login, and a server that refuses SFTP on the terminal's session gets a tab with its own login as before. See [Opening from a terminal tab](../features/sftp.md#opening-from-a-terminal-tab).
- **A remote files sidebar that follows the shell** — seeing the files of the folder you had just `cd`'d into meant opening the SFTP Manager and browsing there by hand. *View → Remote Files Sidebar* now docks a file list beside the panes of every terminal tab (off by default, right or left, width remembered) that lists the folder the focused SSH pane's shell is in, over that pane's own session. It follows folders the shell reports at once and a typed `cd` only after the next prompt shows the session's own user, pauses with a banner while another user or host is active, can be pinned, and only browses — it never types into the terminal. Uploads, downloads and drops go through the transfer list after a confirmation that names the server folder, and are greyed out up front when your organization switches file transfer off. See [Remote files sidebar](../features/terminal.md#remote-files-sidebar).
- **Uploads and downloads ask before they replace a file** — the SFTP Manager replaced a file of the same name on the server or on your computer without a word. It now shows **File already exists** with the size and time of both files and offers **Replace**, **Skip**, **Keep both** (a numbered name such as `report (1).txt`) and **Cancel transfer**, with one answer for all remaining conflicts of the same kind; a symbolic link is never replaced, and a folder still merges into a folder of the same name.
- **A transfer list with progress, Cancel, Retry and resume** — uploads and downloads in the SFTP Manager ran one file after another without progress, could not be stopped, and opened one error dialog per failed file. They now run up to three at a time in a **Transfers** list at the bottom of the tab with progress, speed and time left per file or folder, **Cancel**, **Retry**, **Cancel all** and **Clear finished**; failures become red rows plus one summary at the end. Files are written as `name.kortty-part` and renamed when complete, and **Retry** after a failure or a lost connection continues an interrupted file where it stopped. See [Transfer list](../features/sftp.md#transfer-list).
- **SFTP tabs ask before they close under running transfers** — closing an SFTP Manager tab, its window or korTTY while files were still transferring stopped them without a word, and an idle tab with auto-close could close itself during a long transfer. Every close path now asks **Cancel *n* running transfers and close?** with **Keep tab open** as the default, and auto-close waits until the transfers are done. A drag to the desktop whose download runs out of time now stops in the middle of the file instead of finishing it in the background. See [Transfer list](../features/sftp.md#transfer-list).
- **Transfer settings for the SFTP Manager** — *Settings → SFTP Manager → Transfers* now sets how many files are copied at once (1 to 8, default 3), whether an existing target is asked about, skipped or overwritten, whether interrupted transfers resume from their partial file (on by default) and whether a cancelled transfer keeps its partial file for later. See [SFTP Manager settings](../reference/settings/sftp.md#transfers).
- **Organizations can switch file transfer off** — the new `file-transfer` policy key refuses uploads, downloads, drops and dragging files out of the SFTP Manager, rejects files dragged onto a terminal pane while you drag, greys out the Snippet Manager's copy-to-terminal items for SSH tabs, and fails the JobScheduler's SFTP upload, download and sync jobs and its rsync jobs before they connect, while browsing and remote-only operations keep working; `[rule.sftp]` caps the parallel transfers and sets and locks the answer to existing files. See [Policy configuration](../reference/enterprise-policy.md#rulesftp).
- **Downloads cannot write outside the target folder on Windows** — a server file named after a Windows device such as `CON`, `NUL` or `COM1` (also with an extension, as in `nul.txt`), or a name ending in a dot or a space or containing `:`, was handed to Windows as is, which writes such names to a device or to a different file. The SFTP Manager now refuses these names with an error for that file, and the transfer goes on with the others. See [Uploading files and folders](../features/sftp.md#uploading-files-and-folders).
- **Robust uploads, a responsive server list and Reconnect** — uploading a folder that already existed on the server failed at once; it now merges into the remote folder, and uploads are streamed, so files larger than the available memory or 2 GB no longer fail. Remote folders load in the background behind a **Loading…** indicator, and a folder that cannot be opened keeps the one you were in. A remote copy onto the item itself or into one of its own subfolders is now refused — copying a file to the folder it was in used to empty it. When the connection drops, the status bar shows **Disconnected from** *host* with **Reconnect** instead of Upload, Download and Refresh silently doing nothing. **Size** now sorts by the real byte count, the permissions fields accept only three octal digits, the menu entry is documented as *Connections → SFTP-Client...*, and the German UI says *Server* instead of *Fernbedienung*. See [SFTP file manager](../features/sftp.md).
- **SFTP tabs come back with a project, at their folders** — a saved project referred to its SFTP Manager tabs by connection name while opening it looked them up by id, so with **Auto-Reconnect** no SFTP tab was ever restored, and the saved folders were ignored as well. Tabs are now saved by connection id and reopen at the local and remote folders they showed; a project saved earlier still restores a tab whose connection name is unique. A remote folder that is gone opens the login directory with a note in the status bar. Remote image tabs are saved with the connection they were opened from instead of the first SFTP tab's, so with several SFTP tabs open they no longer reopen from the wrong server. Restored remote image tabs now also connect with a key from the SSH key manager or through a jump server with a stored password, and close their own connection when you close them. See [SFTP Manager tabs](../features/projects.md#sftp-manager-tabs).
- **Rename, New Folder, drag and drop and wildcard search in the SFTP Manager** — the guide described all four, but the SFTP Manager tab had none of them, and its search treated `*` as a plain character. Both panels now rename with ++f2++ or the context menu, create folders from a toolbar button or the context menu, and delete with ++delete++ after confirmation; a rename never replaces an existing entry. Drag local rows or files from the desktop onto the remote panel to upload them and remote rows onto the local panel to download them, also straight into a folder row; up to 20 files with 16 MB together can be dragged from the server to the desktop. The search understands `*`, `?`, `[abc]` and `{py,sh}` and keeps `..` visible. See [File operations](../features/sftp.md#file-operations) and [Search](../features/sftp.md#search).
- **File editor tabs no longer close with unsaved changes** — the editor of a local or remote file asked about unsaved changes only from its own **Close** button and ++ctrl+w++ inside the editor. The tab's close button, *File > Close Tab* (++cmd+w++ on macOS), *File > Close All Tabs*, opening a project, closing the window and quitting korTTY closed it at once, and the changes were lost. All of them now ask **Save**, **Discard** or **Cancel** first, and **Cancel** keeps the tab open. A save that fails, for example because the SFTP connection is gone, now keeps the tab open with your changes instead of closing it anyway. See [File editor tabs](../features/projects.md#file-editor-tabs).

### Performance

- **Dialogs open noticeably faster** — the WebKit engine is loaded in the background after start instead of on the first dialog that needs it, the AI Manager and the settings dialog build their tabs on first visit, a stored connection's secrets are no longer re-derived on every open, and the snippet editor keeps a ready editor in reserve. Measured on a development build, the first AI Manager open dropped from about 1.4 s to under 0.1 s and the settings dialog from about 350 ms to 45 ms. The spare editor can be switched off with **Keep a pre-warmed editor ready**. See [Snippet Editor settings](../reference/settings/snippet-editor/index.md).

### Guide and snippets

- **The built-in guide has a new look and a working offline search** — the guide now uses the Dracula theme, because the previous theme reaches end of life in November 2026. Search works without a network connection and suggests results as you type, and German pages now declare German as their language, so screen readers and hyphenation use the right one.
- **Clearer coding-agents diagram and a wider guide search field** — the diagram on the coding-agents page shows one short note per box and no longer routes a line through other boxes, and the search field in the guide header is wide enough for its German placeholder.
- **Flow diagrams keep loops a model drew in the wrong shape** — when a model drew a loop's condition as a plain action with two exits, the repair cut the exit after the loop and the whole diagram was replaced by the local fallback. Such a loop head is now turned into the loop decision.
- **Flow diagrams from Nemotron and gpt-oss are no longer thrown away** — a model that writes all branches of a decision in one chain through **Stop** (`… --> stop_1 -->|no| failure`), as Nvidia Nemotron does, now gets that chain read as the decision's next outcome instead of the diagram being rejected, and repeated lines no longer make a complete diagram look hollowed out. Rounded nodes such as `setup("Setup" )` are read as actions. When a diagram is still rejected — for example because a local model such as gpt-oss derailed into garbled output — korTTY asks once more, naming the reason, before it uses the local fallback.
- **Snippet Manager: more columns, resizable and remembered** — the snippet table shows **Lines** and **Last modified**, every column (including **Used**, which was too narrow to read, and **Tags**) can be resized, and korTTY remembers the widths. **Export** now proposes plain text script files first. See [Snippets](../features/snippets.md).
- **Import single text files as snippets** — **Import** accepts plain text files such as `data_test.pl`, several at once; each becomes a snippet named after the file, with the language taken from the file extension. Binary files are skipped. See [Importing text files](../features/snippets.md#importing-text-files).
- **Import and export snippet variables** — the Variable Manager exports all or the selected variables as JSON, XML or YAML and imports them again, asking whether existing values are overwritten. Its windows are larger, and the add/edit dialog explains both fields. See [Variable Manager](../features/snippets.md#variable-manager).

### Snippet Manager and code analysis

- **One workspace for all snippets** — the Snippet Manager shows the library and the snippets you edit side by side: browse in a read-only preview tab, edit in one tab per snippet, find a snippet with quick open (++ctrl+p++), hide the library with ++ctrl+b++, and save or close tabs with ++ctrl+s++ / ++ctrl+w++. The open tabs and the window's size and position come back the next time. See [The Snippet Manager workspace](../features/snippets.md#the-snippet-manager-workspace).
- **Unsaved snippets are never lost** — every way of closing, including closing a main-window tab, opening a project and quitting, asks about unsaved snippet edits, and an editor's unsaved form is kept as a draft that can be restored after a crash.
- **The Full code analysis lives in the editor and is stored** — the analysis is a side panel inside the snippet editor, stored with the snippet the moment it arrives and shown again without a new AI request. A history keeps several analyses per snippet (**Stored analyses per snippet** in the Snippet Editor settings), with pinning, discarding, **Verify** after applying, **Review later**, and an apply run that can be continued even after a restart. The library's new **Analysis** column and filter show which snippets have open findings, a stale analysis or a pending review. See [Full code analysis](../features/snippets.md#full-code-analysis).
- **AI changes are reviewed inside the editor** — improvements, security fixes, AI formatting and the analysis's apply result replace the editor area with a side-by-side review instead of a blocking dialog, so terminals and other editors stay usable.
- **Stop and retry any snippet AI request** — every AI action in the snippet editor shows its running time with **■ Stop** (also ++esc++) and offers **↻ Retry** after a stop or failure; a stopped request really ends on the provider side.
- **Before/after analysis reports** — export the stored analysis as PDF, HTML, Markdown or JSON before or after applying, save the analysed or final script as plain text, and export the reports of several snippets at once as one file or a ZIP.
- **More reliable flow diagrams, and a zoom window** — a diagram the model got wrong is requested once more — repaired with the exact error where it can be — a fallback diagram says why it was used, and a click on the analysis diagram opens it in its own zoomable window.
- **Analyses are part of the backup** — the configuration backup includes the stored snippet analyses, and an unreadable snippet file is moved aside instead of being overwritten.
- **Snippet folders** — organise the library in nested folders shown in a tree above the table, drag snippets and folders to move them, and export a whole folder as a ZIP or a directory that keeps its structure. See [Folders](../features/snippets.md#folders).
- **Executable flag** — each snippet is exported and copied as an executable (755) or a plain (644) file; scripts with a known extension or a shebang are executable automatically, and the flag can be changed in the Exec column or the editor. See [Executable flag](../features/snippets.md#executable-flag).
- **Copy snippets and folders into the terminal directory** — copy selected snippets or a whole folder tree as files into the current directory of an SSH session (over SFTP) or a local shell, with the right file modes and an overwrite/skip choice for existing files. See [Copying files to the terminal directory](../features/snippets.md#copying-files-to-the-terminal-directory).
- **Analyse a folder as one project, and modularize** — the Full code analysis can examine a folder of scripts together and report problems between files, and the new *Propose modularization* option lets the AI split a script into modules that become files in a folder. Results that change several files are reviewed in a window with one tab per file and a directory tree that can be shown or hidden. See [Analysing a folder as one project](../features/snippets.md#analysing-a-folder-as-one-project) and [Modularization](../features/snippets.md#modularization).
- **Shell expansions stay as written, and typed values are stored only on request** — only the built-in placeholders and the variables declared in the Variable Manager are replaced, so `${HOME}`, `${1:-default}` or `${#array[@]}` reach the shell unchanged instead of being sent empty or asked for, `$${name}` writes a literal `${name}`, and `${cursor}` places the caret when a snippet is inserted into an editor. Send to Terminal asks for a declared variable without a value instead of sending it empty, Send to Terminal with Parameters lists every declared variable pre-filled, and a value you type is kept only when you tick **Remember**. Scheduled and swarm script runs still refuse an undeclared `${name}`, and a `#` inside a word such as `$#` no longer cuts a shell line short when a script is sent as a one-liner. See [Placeholder variables](../features/snippets.md#placeholder-variables).
- **Quick open keeps the keys it does not use** — keys pressed while the snippet quick open (++ctrl+p++, ++cmd+p++ on macOS) was showing went on to the editor or the library behind it whenever its search box had no use for them, such as ++f5++, ++ctrl+l++ or ++ctrl+d++. They now stay in the quick open box, which still closes with ++esc++. See [Browsing and editing](../features/snippets.md#browsing-and-editing).

### Credentials

- **Passwords from an external command work on Windows and no longer freeze korTTY** — a credential that fetches its password from a command such as `op`, `bw` or `enpass-cli` now runs it in PowerShell on Windows (it always failed there) and on the host in the Flatpak package. The 10-second limit now really holds: a tool that waits for input, an unlock or Touch ID is stopped together with the processes it started and reported, where it could hang korTTY forever before, and the connection editor fetches the password in the background while the field shows *Retrieving password...*. See [Passwords from an external command](../features/security.md#passwords-from-an-external-command).
- **Credentials moved to Cmd/Ctrl+Shift+M** — *Configuration → Security → Credentials…* now opens with ++cmd+shift+m++ on macOS and ++ctrl+shift+m++ on Windows and Linux; ++cmd+shift+p++ / ++ctrl+shift+p++ no longer opens it. The new key works in every tab, also while a terminal has the focus and with the menu bar hidden, and leaves no character behind in the terminal. ++cmd+m++ / ++ctrl+m++ still opens the Connection Manager. See [Keyboard shortcuts](../reference/keyboard-shortcuts.md#general).
- **Built-in credential environments follow the UI language** — the Credential Manager, the credential editor, the connection editor's credential list and the dashboard showed the four built-in environments as *Produktion*, *Entwicklung*, *Test* and *Staging* in every language. They are now translated like the rest of the interface. Credentials keep the environment they are assigned to, because only the label changed. See [Credential Management](../features/security.md#credential-management).

### Backup and restore

- **GPG backups can be restored** — a GPG backup was saved under the ZIP name `kortty-backup.zip`, so importing it asked for a ZIP password and failed, and even a renamed `.gpg` file could not be restored. GPG backups are now saved as `kortty-backup.zip.gpg` and import without a ZIP password; korTTY reads the format from the file content, so GPG backups made by earlier versions under the `.zip` name restore too. See [Importing a backup](../features/backup.md#importing-a-backup).
- **A failed backup no longer pushes out the last good one** — the new backup is written completely before the current one is rotated into `old-backups/`, rotated GPG backups keep their `.zip.gpg` ending, two backups in the same second no longer overwrite each other, and **Maximum Backups** counts ZIP and GPG backups together. See [Backup retention and cleanup](../features/backup.md#backup-retention-and-cleanup).
- **More of your configuration is backed up** — custom terminal themes, credential environments, saved AI Swarm chats and MLX model registrations are now part of the backup, and after an import korTTY reloads them together with SSH keys, snippet variables and AI chats instead of overwriting the restored files with what it had loaded before. A backup with another master password makes korTTY quit after the import, so you unlock the restored data with that password on the next start.
- **The backup dialogs show their numbers** — the confirmation after creating or importing a backup showed `{0}` instead of the file name, size and number of files.

### Teamwork and terminal recording

- **No more options that did nothing** — the Video Manager no longer offers a **Default format**: recordings were always written as korTTY replay files, and WebM or MKV videos come only from **Export**. A setting saved with the old WebM value still loads. The **Read-only** checkbox is gone from the teamwork source dialog as well, because korTTY never writes back to a teamwork source; a value stored earlier is kept. The [Teamwork](../features/teamwork.md) page now describes the one-way sync as it works. See [Terminal recording](../features/recording.md).

- **Teamwork connections can no longer be edited by mistake** — **Edit** on the Connection Manager's **Teamwork connections** tab opened the connection editor although teamwork connections are read-only, and saving changed the shared connection korTTY had loaded without storing it anywhere, so connecting to it could use the edited values. **Edit** is now unavailable on that tab, in the button column and in the right-click menu, and a teamwork connection can no longer be dragged into another folder, which changed its folder the same way. See [Using teamwork connections](../features/teamwork.md#using-teamwork-connections).

- **No more menu entries that did nothing on the Teamwork tab** — right-clicking a folder or an empty area on the Connection Manager's **Teamwork connections** tab offered **New Folder**, **New...**, **Rename Folder**, **Create Subfolder**, **Disable host key verification**, **Export Folder** and **Delete Folder**, none of which did anything there; the host-key check mark even ticked without relaxing anything. As teamwork connections are read-only, those right-clicks now open no menu. See [Using teamwork connections](../features/teamwork.md#using-teamwork-connections).

### Local data files

- **A crash or a damaged file no longer costs you your connections** — connections, credentials, SSH and GPG keys, environments, themes, scheduled jobs and `master.key` are now replaced atomically and flushed to the disk instead of being rewritten in place, and on macOS and Linux `~/.kortty` and the files holding secrets are made owner-only. A file korTTY cannot parse at startup is moved aside as `<name>.corrupt-<timestamp>` and listed in a notice instead of being overwritten with an empty list, and a file it cannot read at all is left untouched for the session. See [Stored security data](../features/security.md#stored-security-data).
- **An unreadable settings file is repaired instead of reset** — a single character that XML cannot hold anywhere else in the settings (such as a control character in a path, a host name or an AI skill) still made `global-settings.xml` unreadable, and korTTY then started with defaults and overwrote the file on the next save. korTTY now first saves an unchanged copy as `global-settings.xml.unreadable-<timestamp>` (keeping the five newest), retries without those characters and keeps the rest of your settings, and falls back to defaults only when that fails too; a notice at startup says which happened and where the copy is.
